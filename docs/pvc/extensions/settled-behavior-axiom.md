# The Settled-Behavior Axiom

> A general governing principle, not specific to any one document in this set. Referenced directly by [Specialised Component](./specialised-component.md), but applies anywhere a Component, Rendition, or placement decision is being classified. Assumes familiarity with [The Poles](./the-poles.md) §3 and [`view-and-rendition.md`](./view-and-rendition.md) §3's branch/case terminology, which it generalizes from.

---

## A Feature's Components Reflect One Decided Behavior, Not a Menu of Behaviors

A prior question has to be answered honestly before any Component, wrapper, or placement decision can be classified, because getting it wrong silently corrupts every classification downstream of it: **is the behavior a Component embodies actually settled, or is it being treated as settled while still secretly being asked "but what if we also wanted it the other way"?**

This surfaced concretely while working out whether a feature's `SearchInput` should stay independently importable once a capability-added version of it existed (see [Specialised Component](./specialised-component.md) for the full worked case). The first answer given was wrong, and it was wrong for a specific, nameable reason: it invented a hypothetical alternative caller — "some View, somewhere, might want the eager, undebounced version" — as if that hypothetical had the same standing as an actual, current requirement. It does not. **A feature's product behavior is decided once, upstream of any architecture question, and the architecture is built in service of that one decided behavior — not as a hedge across several behaviors it might turn out to have.** If a feature's search is defined as firing on keystroke, "would it ever fire on a Go-button instead" is not a live architectural fork to keep both paths open for. It is a different, not-yet-real feature. Building for it now means building for a feature that does not exist.

This is not a new invention — it is the same instinct already governing two other places in this system, made explicit here because it was violated by omission rather than by contradiction:

- **The Poles' closed-family requirement** ([`the-poles.md`](./the-poles.md) §3: "Global-Local is the deliberate, permanent judgment... not merely because it currently has two consumers and an uncertain future") already refuses to let a *speculative future consumer* justify a placement decision today. This axiom is the same refusal, one layer earlier — applied to a Component's *behavior* rather than its *consumer count*. A Component's behavior must be as settled as its consumer family before either can be classified.
- **[`view-and-rendition.md`](./view-and-rendition.md) §3's own terminology note** ("branch"/"case," never "state") already treats a View's Renditions as the actual, exhaustive, decided set of outcomes for one behavior — never a placeholder for "whichever behavior gets picked later." The settled-behavior axiom is that same discipline, stated as a general rule instead of left implicit in how Renditions happen to be described.

**The rule in full:** when classifying a Component — whether it stands alone, whether a capability wrapper around it is optional or mandatory, whether it should be underscored — ask only what this feature's *actual, current, decided* behavior is. Do not ask what behavior the feature *might* have instead; that is a product question, not an architecture question, and answering it preemptively produces exactly the wrong classification, as it did here. **If the product behavior later genuinely changes, the architecture is rebuilt to match the new settled behavior — it does not hedge in advance by keeping both shapes alive "just in case."** A Component that exists "in case we go back to the other behavior" is dead weight wearing the shape of flexibility.

**A behavior arriving unsettled is not something PVC — or any architecture — can fix.** If a feature is handed to implementation without a decided answer to "does this fire on keystroke or on a Go button," no folder structure, naming convention, or placement rule closes that gap, because the gap isn't architectural — it's a **product decision that was never made**. Building both shapes "to be safe" doesn't resolve the missing decision, it hides it: it produces a codebase that *looks* like it has an answer while actually encoding indecision as two parallel, silently-diverging implementations, each accumulating its own fixes as the real behavior is worked out by trial and error in production rather than by decision beforehand. When a Component can't be classified — when it's unclear whether it should stand alone, be underscored, or be replaced entirely by a Specialised Component — the correct diagnosis is almost never "PVC lacks a rule for this." It is "the product decision this architecture is supposed to reflect hasn't been made yet," and the fix is to go get that decision, not to invent an architectural escape hatch that quietly defers it.
